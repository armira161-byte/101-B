# Рекомендации и открытые вопросы (по состоянию на 2026-09-19)

Этот документ — итог по всей серии сессий рефакторинга варианта А
(SL/TP-геометрия для 41 паттерна), завершения Фазы 5 (бэктест), и
углублённого аудита качества. Разбит на три уровня: то, что блокирует
сборку/работу приложения (сделать в первую очередь), то, что не
блокирует, но искажает точность сигналов или данные, и то, что осталось
открытым продуктовым/архитектурным вопросом.

---

## 0. Прежде всего: почему «должно собираться без ошибок» — не гарантировано мной

Ни разу за всю серию сессий не было доступа к сети/`node_modules` в
песочнице — значит `npm ci`, `npx tsc --noEmit`, `npm test`, `npm run
build`, `npm run lint` **ни разу не запускались** на этом дереве. Все
правки проверялись только: (а) построчным чтением кода, (б) скриптовой
проверкой баланса скобок/кавычек по всем `.ts`/`.tsx` файлам, (в) ручной
сверкой сигнатур импортов/экспортов. Это снижает риск, но не заменяет
компилятор. Один раз в этой самой серии сессий я уже пропустил реальный
баг (`signal.pattern?.name` вместо `signal.pattern`) при чтении и нашёл
его только на отдельном повторном проходе — то есть чтение кода без
компилятора эмпирически ненадёжно даже когда его делают целенаправленно.

**Первое действие после распаковки в bolt.new — не «посмотреть, что
получилось», а буквально:**

```bash
npm ci
npm run build      # = tsc --noEmit -p tsconfig.app.json && vite build — это и есть boлt.new-гейт деплоя
npm run test        # vitest run
npm run lint         # eslint .
```

(`npm run ci` уже объединяет typecheck+lint+test одной командой — см.
`package.json`.) Если `npm run build` падает — это единственный
авторитетный источник истины о том, собирается приложение или нет;
всё, что написано ниже, — best-effort экспертная оценка, не замена этой
команде.

Для проверки миграций Supabase отдельно (см. п.1 ниже) — команда
Supabase CLI зависит от вашей настройки проекта (`supabase db push` или
аналог), нет универсальной команды, которую можно было бы просто
вставить сюда.

## 1. Блокирующее / высокий риск — сделать в первую очередь

### 1.1. Проверить миграцию `20260919120000_fix_trading_signals_sl_tp_columns.sql` на стейджинге ДО прода

Только что исправленная находка: `stop_loss`/`take_profit` могли не
сохраняться в Supabase вовсе (опечатка в имени таблицы в более ранней,
не связанной с вариантом А миграции — `ALTER TABLE signals` вместо
`ALTER TABLE trading_signals`). Новая миграция написана идемпотентно и
безопасно для обоих возможных стартовых состояний таблицы, но **не
проверялась на реальной базе** — нет доступа из песочницы. Обязательно:

```sql
-- до миграции — зафиксировать текущее состояние
select column_name, is_nullable from information_schema.columns
where table_name = 'trading_signals' and column_name in
  ('stop_loss','take_profit','expiry_bars','estimated_pattern_maturity_bars');

-- после миграции — стоп_лосс/тейк_профит должны быть nullable=YES,
-- expiry_bars/estimated_pattern_maturity_bars — nullable=NO
```

и вручную сохранить/прочитать один тестовый сигнал через приложение,
убедиться, что `stop_loss`/`take_profit` реально долетают до строки в
Supabase (не `null` для НОВОЙ сделки).

### 1.2. Прогнать полный `npm run ci` и разобрать все ошибки построчно

См. §0. Особое внимание, если что-то упадёт, на файлы, которые
редактировались в этой серии сессий без компилятора под рукой (полный
список — в `docs/changelog/`, начиная с `CHANGES_APPLIED_
REFACTOR_VARIANT_A_PHASE5_20260917.md`). Для системной проверки уже
подготовлен `docs/audit/refactor-variant-A-phase5-verification-
prompt.md` — чек-лист именно на этот случай, можно скормить его
любому инструменту/сессии с реальным доступом к сборке.

### 1.3. Прогнать e2e (Playwright) и просмотреть Sentry после первого деплоя

`e2e/terminal.spec.ts` не запускался и не ревьюился построчно в этой
серии сессий вообще — только один поверхностный `grep` на предмет
явно устаревших полей (ничего не нашлось, но это не то же самое, что
реальный прогон). Аналогично, интеграция с Sentry (`@sentry/react` в
зависимостях, `src/lib/sentry.ts`) не проверялась на предмет того, что
после этих правок не появилось лавины новых ошибок в рантайме.

## 2. Не блокирует сборку, но влияет на точность сигналов/данных

### 2.1. Три новые функции геометрии не откалиброваны на реальных данных

`computeConsolidationBreakoutTradeLevels`/`computeInsideBarTradeLevels`/
`computeMeanReversionTradeLevels` (добавлены в этой серии сессий) —
геометрия выведена логически из структуры, которую уже вычисляет каждый
детектор (границы диапазона, диапазон материнской свечи, средняя полоса
Боллинджера), а не из бэктеста. Это стандартная, объяснимая геометрия
(measured move, средняя полоса), но её реальные winRate/averageR на этом
конкретном наборе паттернов и порогов confidence — неизвестны. Рекомендация:

```bash
npm run backtest:horizon-calibration -- --symbol=EURUSD --from=2025-01-01 --to=2025-06-01 --timeframe=15m
npm run backtest -- --symbol=EURUSD --from=2025-01-01 --to=2025-06-01 --timeframe=15m
```

и явно посмотреть на `winRate`/`averageR`/`averageWinR` именно по этим
трём паттернам в отчёте (`backtest/report.ts` группирует по паттерну).
Юнит-тестов на геометрию (не на сам детектор — они есть) для этих трёх
функций тоже не написано в этой сессии.

### 2.2. `CalibrationPanel.tsx` всё ещё использует нерелевантную экономику для точки безубыточности

`breakevenWinRateFromProfitPercent(useDemoAccountStore.profitPercent)` —
`profitPercent` с Фазы 4 (позиционная модель P&L) больше не участвует в
реальном расчёте прибыли демо-счёта (оставлено в публичном API стора
намеренно, для обратной совместимости, см. комментарий в
`useDemoAccountStore.ts`). Панель калибровки поэтому показывает точку
безубыточности, которая не отражает реальную экономику сделок. Для
бэктеста аналогичная проблема уже решена (`backtest/change-registry.ts::
breakevenWinRateFromAverageWinR`, выводится из реального среднего R
победных сделок той же выборки) — тот же принцип можно перенести в live
`CalibrationPanel.tsx`, но это требует агрегации среднего R реальных
демо-сделок в `useAnalyticsStore`/`useDemoAccountStore` (которой сейчас
нет) — отдельная, не тривиальная задача, не взятая в эту серию сессий
намеренно (см. «Фаза 6» ниже).

### 2.3. Горизонты резолва (`HORIZON_BARS_BY_CLASS`) — всё ещё гипотеза, не результат бэктеста

`backtest/horizon-calibration.ts` (сетка `{5,10,20,30,50}` по паттернам)
написан и готов к использованию, но **ни разу не запускался на реальных
исторических данных** — числа в `src/decision/pattern-horizon.ts` по-
прежнему основаны на качественной гипотезе ("вероятно короткие/средние/
длинные"), не на измеренном оптимуме. Промт (Фаза 2/5) явно предполагает
именно такой порядок: гипотеза → бэктест-сетка → финальное число.
Рекомендуется прогнать на нескольких инструментах/периодах, не на одном
срезе (см. предупреждение внутри самого скрипта про Walk-Forward
протокол).

## 3. Открытые продуктовые вопросы (не техническая необходимость, решение — за вами)

Эти вопросы поднимались промтом изначально и не были формально закрыты
ни одной из сессий:

- **Судьба `recommended_expiry`** (старая колонка Supabase, adaptive-
  оценка в секундах) — физически не тронута ни одной миграцией этой
  серии, но и не используется текущим кодом. Оставить как исторический
  артефакт, или явно удалить отдельной миграцией — решение продукта, не
  технический блокер.
- **Легаси-тумблер мартингейла** (если такой существует в `settingsStore`/
  UI — не проверялся отдельно в этой серии сессий) — судьба не
  пересматривалась.
- **Полная ревизия UI под реальные SL/TP (Фаза 6 промта)** — не начата.
  Помимо `CalibrationPanel.tsx` (см. §2.2), стоит отдельно пройтись по
  всем местам, где приложение показывает пользователю языковые
  конструкции в духе "экспирация через N баров" без упоминания
  стоп-лосса/тейк-профита — `SignalCard.tsx`/`trade-report.ts` уже
  приведены в порядок (предыдущие сессии), но не проверялось, есть ли
  другие такие места (например, `TradeHistoryPanel`, если он существует,
  не проверялся).
- **Регрессия по полному чек-листу (Фаза 7 промта)** — не проводилась
  вообще ни разу за всю серию сессий. Теперь, когда
  `docs/audit/pattern-audit-checklist.md` наконец корректен (см.
  находку в `CHANGES_APPLIED_DEEP_AUDIT_VARIANT_A_20260919.md`), эта
  фаза стала осмысленной и её стоит провести: для каждого из 41
  паттерна — сверить реализованную геометрию с `sltp-geometry-source-
  variant-A.md`, а ещё лучше — с независимым источником (учебником/
  статьёй по конкретному паттерну), не только со внутренней
  самосогласованностью кода.
