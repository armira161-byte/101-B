# Критическая находка: stop_loss/take_profit не сохранялись в Supabase вовсе

Дата: 2026-09-19. Найдено при подготовке итоговых рекомендаций — не было
частью предыдущих сессий, вскрылось при построчной сверке
`signal-persistence.ts` с реальными файлами миграций Supabase.

## Что произошло

`supabase/migrations/20260915120000_binary_options_refactor_drop_sl_tp_
expiry.sql` (более ранняя, отдельная от варианта А сессия — "бинарные
опционы, Фаза −1/0/1") содержит `ALTER TABLE signals ...` — обращение к
таблице `signals`. Реальная таблица называется `trading_signals` (создана
в `20260804012847_create_trading_signals_tables.sql`). Таблицы `signals`
в проекте не существует ни в одной миграции — то есть при реальном накате
эта миграция должна была упасть на первом же операторе с ошибкой
Postgres "relation \"signals\" does not exist".

Практическое следствие: фактическое состояние `trading_signals` в любой
конкретной инсталляции неизвестно заранее (либо исходная схема
до `stop_loss`/`take_profit`/`recommended_expiry`, либо, если кто-то
вручную поправил имя таблицы при накате, — схема после миграции). Но код
(`src/lib/signal-persistence.ts`) был написан ТОЛЬКО под "схему после" —
`SignalRow` не содержал `stop_loss`/`take_profit` вовсе. Это означает, что
для сигналов, сгенерированных вариантом А (где `Signal.stopLoss`/
`Signal.takeProfit` — обязательные поля с реальной геометрией для всех 41
паттерна), эти два значения:
- никогда не отправлялись в Supabase при сохранении (`signalToRow()` их
  просто не включал в объект — если в реальной таблице колонки `stop_loss`/
  `take_profit` всё ещё `NOT NULL` без дефолта, каждый `saveSignal()` должен
  был возвращать ошибку INSERT/UPSERT, проглатываемую try/catch как "Non-
  fatal: app works in-memory without persistence" — то есть сохранение
  сигналов в БД могло быть полностью сломано молча, без единого видимого
  симптома в UI);
- никогда не восстанавливались при чтении (`rowToSignal()` не
  устанавливал `stopLoss`/`takeProfit` вовсе — при обязательных полях
  типа `Signal` это ещё и прямая TS-ошибка компиляции, не только
  runtime-потеря данных).

## Исправление

1. **Новая корректирующая миграция**
   `20260919120000_fix_trading_signals_sl_tp_columns.sql` — идемпотентна,
   безопасна независимо от того, в каком из двух возможных состояний
   реально находится `trading_signals` на конкретной инсталляции
   (`ADD COLUMN IF NOT EXISTS` + `DROP NOT NULL`, без разрушительных
   операций). `stop_loss`/`take_profit` становятся nullable (честно:
   старые строки, если их реально когда-то удалили сломанной миграцией, —
   не бэкофилятся выдуманными числами).
2. **`src/lib/signal-persistence.ts`**: `SignalRow` получил
   `stop_loss`/`take_profit` (`number | null`); `signalToRow()` теперь
   реально пишет `s.stopLoss`/`s.takeProfit` (всегда настоящие значения —
   поля обязательны на уровне типа `Signal`); `rowToSignal()` читает их с
   явно помеченным синтетическим фолбэком (±1% от `entry_price`) **только**
   для строк, где в БД реально `NULL` (исторический брак сохранения) — не
   для новых сделок.

## Не сделано / требует внимания оператора БД

- Старая миграция `20260915120000` НЕ отредактирована по существу
  (иммутабельность истории миграций) — только добавлен поясняющий
  комментарий в начало файла.
- Эта правка НЕ проверялась на реальной Supabase-инстанции (нет доступа
  из песочницы) — перед продакшеном обязательно накатить миграцию на
  стейджинге и проверить `select stop_loss, take_profit from
  trading_signals limit 5` до и после.
- `recommended_expiry` (старая колонка, adaptive-оценка в секундах) — не
  восстановлена и не используется текущим кодом; оставлена как есть,
  дальнейшая судьба — решение продукта, не техническая необходимость.
