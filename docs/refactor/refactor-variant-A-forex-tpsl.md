## Что изменилось по сравнению с редакцией 2

Вся геометрия SL/TP, которой оперирует Фаза 0' (что считать стопом/целью для каждого из ~28 детекторов), больше не основана только на общей price-action/SMC-эрудиции — она сверена по внешним источникам (ICT-ресурсы, Wyckoff-ресурсы, справочники по гармоникам, статистика Bulkowski, литература по ATR-стопам) и зафиксирована в отдельном обязательном документе `sltp-geometry-source-variant-A.md`. Без него Фаза 0' не имеет смысла начинать — это прямое требование к этой редакции промта.

Сверка выявила **три содержательных уточнения** относительно редакции 2 (не отменяющих её, а исправляющих конкретные пункты — подробности и обоснование в `sltp-geometry-source-variant-A.md`, где также приведена полная сводная таблица исправлений):

1. **`order-block-breaker.ts`** — стоп ставится не за экстремумом самого breaker-блока, а за хвостом свечи снятия ликвидности, которая привела к его формированию (это разные уровни).
2. **`liquidity-sweep.ts`, `setupType==='reversal-at-key-level'`** (методологически = Wyckoff Spring/Upthrust) — цель не «ближайшая противоположная зона через `smartMoney`» (это верно только для `setupType==='continuation'`), а противоположная граница локального Trading Range.
3. **`harmonic-pattern.ts`** — уже подключённая (Группа 1, "✅ own") функция `computeHarmonicTradeLevels()` требует проверки: стоп должен различаться по подсемейству гармоник (Gartley/Bat — за точкой X; Butterfly/Crab — за точкой D), единая формула на все гармоники методологически неточна.

Плюс некритичное, но полезное для интерпретации Фазы 5 наблюдение: Rising/Falling Three Methods по независимой статистике — редкий паттерн, на M1-данных стоит заранее закладывать риск маленькой выборки сигналов в бэктесте.

## Фаза −1 — точка форка и что делать с кодом, не относящимся к этому репозиторию

**Точка форка**: текущий HEAD `project-bolt-github-q9vx84pr` (с уже применёнными `Fix #1/#2/#4`), **до** начала Фазы 0'/Фазы 1 обоих вариантов. Оба репозитория расходятся из одного и того же коммита; вариант А получает рабочее название, например `project-bolt-forex-tpsl`, и с этого момента развивается независимо от `project-bolt-binary-options` (вариант Б) — переносить коммиты/фиксы между ними вручную, не через общий upstream.

**Что удалять сразу при форке**: ничего. На момент форка кодовая база сама по себе парадигмо-нейтральна — поля `stopLoss`/`takeProfit`/`recommendedExpiry`/`barsToResolve` в `types/domain.ts`, generic-фолбэк `estimateTradeLevels()`, бинарно-опционная экономика демо-счёта — это ровно то сырьё, с которым Фазы 0'-6 варианта А работают дальше. Ничего из этого не является "чужим" кодом варианта Б (вариант Б ещё не реализован ни на одном коммите этой истории), удалять на входе нечего.

**Что становится чужим/подлежит удалению по ходу работы (не оставлять как мёртвый код "на всякий случай"):**

1. После завершения Фазы 4 (переход демо-счёта на позиционную модель P&L) — **удалить** старый путь `pnl = stake * profitPercent / 100` из `useDemoAccountStore.ts` полностью, не оставлять его как альтернативную ветку/feature-flag "на случай отката". Если мартингейл-режим сохраняется как legacy-опция (см. "Открытые вопросы" п.3) — это осознанно оставленная фича с явным UI-тумблером, а не забытая ветка кода; если продукт решает мартингейл не оставлять — удалить весь код стадий (`stage`/`stageAmounts`/`halted`) целиком, а не выключать флагом.
2. После завершения Фазы 0' (все ~28 паттернов получили собственную `computeXxxTradeLevels()` — см. чек-лист) — **удалить** generic-фолбэк `estimateTradeLevels()` из `trade-levels.ts` как основной путь для паттернов. Если он используется как safety-net на случай нового, ещё не классифицированного паттерна — оставить только с явным предупреждением/логом ("паттерн X использует неаудированный фолбэк"), не как молчаливый дефолт для четверти всех детекторов, как сейчас.
3. Собственная копия `pattern-audit-checklist.md` в этом репозитории — **удалить** из неё колонку "Действие Б" и всю колонку "Backtest: лучший `expiryBars`" в её accuracy-прочтении (эта метрика — не то, что здесь измеряется, см. Фазу 5 п.2). Не оставлять пустые/нерелевантные колонки "на будущее" — они создают риск, что кто-то впишет туда число в чужом смысле.
4. `recommended-expiry.ts` — этот модуль в варианте Б переименовывается в `estimatedPatternMaturityBars`-семантику (см. промт варианта Б, Фаза 0). В этом репозитории переименование не нужно и не переносится — модуль остаётся как есть, под своим текущим именем и смыслом ("оценка, сколько баров обычно нужно паттерну").



Два независимых определения исхода — паттерны считают TP/SL для многобаровой сделки, а `resolveOutcome()`/`resolveTrade()` резолвят по цене закрытия ровно следующей свечи — должны схлопнуться в одно. Частичный фикс (починили резолв, но не демо-счёт, или наоборот) воспроизведёт уже однажды случившееся расхождение "Последние сделки" vs "История сигналов". Все шесть фаз ниже обязательны и должны катиться вместе, одним PR-деревом, а не по одной в продакшен.

## Фаза 0' — достроить структурную обвязку TP/SL по паттернам

Источник задач — `pattern-audit-checklist.md`, группы 2-4 (геометрия в чек-листе уже приведена в соответствие с `sltp-geometry-source-variant-A.md`). Порядок работы:

1. **Группа 2 (SMC/ICT без обвязки)** — 9 паттернов (`strong-order-block-reaction`, `macd-deceleration-continuation`, `fvg-return`, `fvg-rejection`, `fvg-breaker-block`, `fvg-nested`, `order-block-breaker`, `order-block-nested`, `liquidity-sweep` база). Для каждого — написать `computeXxxTradeLevels()` в `trade-levels.ts` по конкретной геометрии, уже зафиксированной в чек-листе (например, для `fvg-rejection`: SL = граница FVG минус/плюс buffer, TP = ближайшая противоположная зона через `smartMoney`). Где чек-лист указывает на переиспользование общей функции (`computeFvgTradeLevels()` для всего fvg-семейства, общий `computeThreeMethodsTradeLevels()` для Rising/Falling) — не плодить дублирующиеся функции, консолидировать сразу.
   - **`liquidity-sweep.ts`** (база, не -reaction) — ⚠️ после сверки с источниками это **не** самый дешёвый пункт списка, как считалось в редакции 2: детектору по-прежнему не хватает `sweepLow`/`sweepHigh` (= `last.low`/`last.high`) в `PatternResult`, но существующую `computeLiquiditySweepTradeLevels()` нельзя просто подключить "как есть" — она не различает цель по `setupType` (см. `sltp-geometry-source-variant-A.md`, п.3: `reversal-at-key-level` требует цели по границе локального Trading Range, а не через `smartMoney`). Нужна доработанная версия функции с веткой по `setupType`, включая логику определения границ диапазона для Spring/Upthrust-сценария.
   - **`order-block-breaker.ts`** — источник SL — экстремум свечи снятия ликвидности, предшествующей формированию breaker, а не экстремум самого блока (см. `sltp-geometry-source-variant-A.md`, п.1). Проверить, доступен ли этот sweep-экстремум в текущем `PatternResult` детектора; если нет — добавить.
2. **Группа 3 (классические свечные — `single.ts`/`double.ts`/`triple.ts`/`pin-bar.ts`)** — геометрия стопа у большинства из них идентична внутри семейства (экстремум 2- или 3-барной формации ± buffer×ATR) — не писать 21 отдельную функцию, а сделать **параметризованные по направлению общие хелперы**:
   - `computeTwoCandleExtremeLevels(prevCandle, curCandle, direction, atrValue)` — покрывает Engulfing (оба), Harami (оба), Piercing Line, Dark Cloud Cover, Tweezer (оба) — у всех восьми стоп берётся одинаково: экстремум объединённой 2-барной формации.
   - `computeSingleCandleWickLevels(patternCandle, direction, atrValue)` — покрывает Hammer/Shooting Star/Inverted Hammer/Hanging Man/Marubozu (оба) — стоп за хвостом/экстремумом самой свечи.
   - `computeThreeCandleExtremeLevels(a, b, c, direction, atrValue)` — покрывает Morning/Evening Star, Three Soldiers/Crows, Abandoned Baby (оба) — с параметром, какая из трёх свечей даёт экстремум (для Star-семейства это `min(a,b)`/`max(a,b)`, для Abandoned Baby — именно `b`, средняя "покинутая" свеча — не путать местами, см. чек-лист построчно).
   - `computePinBarLevels(patternCandle, direction, atrValue, smartMoney, structure)` — единственный в этой группе, кому нужна конфлюэнс-логика для TP (ближайшая зона `smartMoney`/swing), не просто measured move.
   - Для TP внутри группы 3, где нет ближайшей структурной зоны — использовать measured-move фолбэк (высота формации, не голый ATR×2) там, где чек-лист явно это указывает (Marubozu, Rising/Falling Three Methods), иначе — ближайший структурный уровень с фолбэком на ATR×2.
   - **Doji и Spinning Top** — не подключать к TP/SL вообще, пока не решён продуктовый вопрос "должны ли они быть самостоятельными сигналами" (см. чек-лист, Группа 3, примечание) — это не техническая задача этой фазы.
3. **Группа 4 (`continuation.ts`)** — Rising/Falling Three Methods, единая `computeThreeMethodsTradeLevels()`, TP = measured move от высоты импульсной свечи 1, а не ATR×2 (см. конкретную формулу в чек-листе).
4. После каждой новой `computeXxxTradeLevels()` — юнит-тест на синтетических свечах с заранее известными high/low/close, проверяющий именно то значение SL/TP, которое задокументировано в чек-листе для этого паттерна (не просто "SL не null").
